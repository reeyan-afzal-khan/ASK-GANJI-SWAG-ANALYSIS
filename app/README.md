# Ask Ganji Swag Analytics app

An interactive, static web app for exploring the 1,422 viewer questions answered on Ask Ganji Swag, listed in the [episode index](../docs/episode-index.md). It shows what people ask about, which of 10 categories and 60 subcategories each question falls into, and how that changed across 242 episodes. It also covers how long each subject is discussed, askers' stated ages, and the places they mention. The episode explorer plays each episode in a built-in YouTube player, with the transcript following the video line by line and the question being answered shown as it plays.

It is plain HTML, CSS and JavaScript with no external libraries. Everything it reads is generated into `data/`, so this folder works on its own: open `index.html` from disk, preview it locally, or publish it on any static host such as GitHub Pages. The only outside requests go to YouTube, when you open the episode explorer: its player (in privacy-enhanced mode) and video thumbnails. YouTube only plays embedded videos on pages served over http(s), so opened from disk the explorer shows the transcript and opens timestamps on YouTube instead.

## Layout

```text
app/
├── index.html          # The app
├── assets/             # app.css, app.js, the logo, and theme.css (generated from skins/)
├── skins/              # Colour themes: one light and one dark JSON file
├── data/               # Generated by run.sh; do not edit by hand
│   ├── summary.js      # Questions, categories, episodes and word statistics
│   └── transcripts/    # One file per episode for the transcript in the episode explorer
├── tools/
│   ├── build_data.py   # Builds data/ from the Roman SRTs, the episode index and the labels
│   ├── question_labels.json  # Hand-checked subcategory of every question, one line per episode
│   ├── config.json     # Categories, subcategories, fallback keywords, places and stopwords
│   └── test_build_data.py
├── run.sh              # Build data/; --serve previews the app
└── .nojekyll           # Tells GitHub Pages to publish files as they are
```

## Build and preview

Run these from the repository root, in Ubuntu/WSL2 or any Bash:

```bash
# Rebuild data/ after new transcripts or index entries.
bash app/run.sh

# Rebuild, then preview at http://localhost:8765/ exactly as a static host would serve it.
bash app/run.sh --serve
```

The builder uses only Python's standard library, and it also regenerates `assets/theme.css` from `skins/`. On Windows, `python app\tools\build_data.py --serve` does the same. In WSL2, open the printed address in your Windows browser; Ctrl+C stops the preview. Use the preview, not the file on disk, to try the episode explorer's player. Unchanged data files are left untouched, so rebuilding without new input produces no Git changes. `bash scripts/08-test/run.sh` runs the builder's tests with the rest of the repository's tests.

## Categories

Each question's category comes from `tools/question_labels.json`. The file has one line per episode with a code for each question, in index order:

```json
"7": ["love.marriage", "career.path edu.choice", "money.struggle", ...]
```

The first code is the question's subcategory, and any further codes are clear second subjects. All codes are defined, with names and descriptions, in `tools/config.json`. The labels were assigned by reading each title and, where a title was vague, the opening of the answer, which is usually the letter being read out. To correct one, edit its code and rebuild; an unknown code stops the build and names the episode and question.

After you add a new episode to the index, add its line here too. Until then its questions are placed by the keyword lists in `config.json` and appear as "Not yet sorted". The build output and the app's **About** tab both list such episodes.

Broad subjects are split into finer subcategories under the same category: love and marriage, for example, has separate subcategories for rishtas, choosing a partner, love across caste, faith and borders, marriage problems and difficult spouses. To add a subcategory, define it in `config.json` under its category, use its code in the labels file and rebuild; the sidebar, charts and tables pick it up on their own.

## Colours and skins

`skins/` holds the colour themes as JSON: the brand orange from the logo as the accent, white or black backgrounds, and the eight category colours, all checked for colour-blind separation and contrast. `bash app/run.sh` turns the first light skin and the first dark skin (by their `order`) into `assets/theme.css`, which the page loads before `app.css`. Visitors get the theme that matches their system, or pick Auto, Light or Dark in the sidebar. To change a colour, edit the skin and rebuild; the build stops and names any token a skin is missing.

## Publish on GitHub Pages

The data is about 58 MB in total, with the English transcripts (about 1.5 MB loads on first visit; transcripts load on demand), well within GitHub Pages limits. Commit `app/data/` after each rebuild so the published site stays current. Choose one of the following:

- **From this repository with GitHub Actions.** In the repository's *Settings → Pages*, set *Source* to *GitHub Actions* and use a workflow that uploads the `app/` folder as the Pages artifact. The site is then `https://<username>.github.io/<repository>/`.
- **From this repository's branch, with no workflow.** Pages can only publish the repository root or `docs/`, so choose the `main` branch and `/ (root)`. The app is then at `https://<username>.github.io/<repository>/app/`, and the `index.html` at the repository root forwards the site's front page there, so the root address opens the dashboard rather than the README. This publishes every tracked file in the repository; add an empty `.nojekyll` at the root to skip Jekyll processing. This is how the site is published now.
- **From your user site.** Copy this folder's contents into your `<username>.github.io` repository, at its root or in a subfolder such as `ask-ganji/`, and push. Only `index.html`, `assets/`, `data/` and `.nojekyll` are needed there; `tools/` and `run.sh` stay here for rebuilding.

All links inside the app are relative, so it works at any of these addresses. The page describes itself as an unofficial, fan-made analysis, and the episodes and their content belong to their creators.
